# Дайджест с инсайтами: facet-отметки и отдельное сообщение с релизами

Статус: реализовано (2026-11-10), флаги `digest.insights` и `digest.releases_message` по умолчанию `false`; включение в реальном `.config.yaml` ждёт решения владельца. Автор: Claude по итогам брейншторма с владельцем.
Всё, что помечено «моё решение», владелец не формулировал; проверьте при чтении.

## Зачем

Владелец читает Telegram-дайджест целиком и всё равно не понимает, что стоит за строкой. Его цель:
узнавать, какие технологии и идеи **появляются, реализуются и набирают силу**, и понимать,
**чем проект отличается от других в своём классе**.

Сегодня:

- `🚀`-релизы занимают весь лимит 10 пунктов на домен (общий для всех секций), поэтому новое и растущее
  вытесняется. Релизы сортируются только по звёздам.
- Строка релиза это `owner/name` + тег. Описания, звёзд и ответов Decider нет, по названию непонятно, что за проект.
- «…and N more» это пункты, не влезшие в лимит. Они помечаются обработанными и **больше нигде не появляются**.
- Иконки (`🚀 🆕 🔎 📈`) нигде не расшифрованы. Порядок строк объяснить нельзя.

Успех: за несколько секунд видно новое и растущее; у каждого проекта видно, в чём он необычен;
релизы не пропадают, но не мешают.

## Цели

1. Основной дайджест (слот 08:30, как сейчас) показывает **только новое и растущее**: 🆕, 🔎, 📈
   (и изменения стека, см. «Оставлено builder'у»).
2. У каждого пункта: описание в одну строку, звёзды, `kind · lvl`, **facet-отметки**.
3. Отдельное Telegram-сообщение **раз в день** с релизами (это выбор владельца).
4. Расшифровка иконок в сообщении. «…and N more» заменяется счётчиком по типам и командой для полного списка.
5. Facet-отметки строятся из ответов Decider на вопросы домена (`triage.questions`).

## Нет-цели и анти-цели

- Не ломать repka: существующее поведение сохраняется, пока новое не включено.
- Нет real-time уведомлений (глобальное ограничение 11 проекта): релизы идут раз в день по расписанию.
- Нет пересказа проекта моделью (summary от LLM): только фиксированные вопросы Decider.
- Нет облачных моделей (`triage.allow_remote` остаётся `false`). Данные не покидают машину, кроме GitHub и Telegram.
- Не меняем пороги `triage.thresholds` и критерии `accepted`: facet-вопросы на принятие не влияют.
- Анти-цель: отметки, которые есть у всех проектов (шум). Это хуже, чем отсутствие отметок.

## Принятые решения

**Класс.** Класс это домен: репозиторий входит в класс, если Decider ответил «да» на `relevant`
относительно `profile` домена. Отличия внутри класса выражаются ответами на дополнительные вопросы.

**Facet-вопросы (уже записаны в `domains/*.yaml`, по 5 на домен, тип `noul`):**

- `ai-agent-harness`: `self_modifies`, `uses_own_models`, `trains_weights`, `sandbox`, `subagents`.
- `mcp`: `remote_transport`, `gateway`, `guardrails`, `token_efficiency`, `wraps_service`.

Пробный прогон на 30 принятых репозиториях (копия `REPKA_HOME`, без Telegram, база не менялась):

- хорошо различают: `self_modifies`, `trains_weights`, `subagents`, `gateway`, `guardrails`, `wraps_service`;
- слабо или бесполезно (почти у всех одинаково): `sandbox`, `uses_own_models`, `remote_transport`, `token_efficiency`.

Владелец решил оставить все 10 вопросов и **оценивать по результатам**. Слабые вопросы можно заменить или убрать
после того, как перетриаж накопит данные (см. «Оценка»).

**Основной дайджест (макет согласован).**

- Секции по доменам, внутри 🆕 / 🔎 / 📈. Релизов в нём нет.
- Под названием проекта: описание в одну строку (обрезается), затем `kind · lvl N` и facet-отметки.
- Отметка показывается, если `p >= digest.facet_min_p` (моё решение: 0.7; настраиваемый ключ).
- Максимум 3 отметки на проект, с наибольшим `p` (моё решение).
- Легенда иконок одной строкой внизу.
- Вместо «…and N more»: счётчик по типам, например «…and 12 more: 5 🆕, 7 🔎», плюс команда для полного списка
  (`repka digest --more`, моё решение по имени). Для этого пункты, не влезшие в лимит, **не должны теряться**:
  они не помечаются обработанными до тех пор, пока не показаны (сегодня они помечаются сразу; это изменение
  семантики, сделать осознанно, с тестом).

**Сообщение с релизами (макет согласован).**

- Отдельное сообщение раз в день, по собственному слоту (ключ вроде `digest.releases_slot`, моё решение по имени).
- Секции по доменам: «N releases», по каждому проекту `★звёзды · тег`, сортировка по звёздам, лимит строк на домен,
  затем «…and N more».
- Facet-отметок в релизах нет.
- Команда для полного списка: `repka releases --since 24h` (моё решение по имени).
- Пустое сообщение не отправляется (глобальное ограничение 11).

**Флаги.** Всё новое включается флагами в `.config.yaml`, **по умолчанию `false`** (глобальное правило владельца
и проекта). Предложение (моё решение): `digest.insights: false` (новый формат основного дайджеста без релизов)
и `digest.releases_message: false`. Пока флаги выключены, дайджест остаётся как сегодня.

## Семантика, уточнённая после проверки (всё это моё решение)

**Учёт отправки релизов.** Сообщение с релизами это отдельная запись в `digests` (тип `releases`, ключ
`(kind, slot, local_date)`, нужна миграция схемы, как для `P2-T03`: `migrate()` должна оставаться безопасной при
гонке). События `release` помечаются отправленными **только после успешной отправки** этого сообщения, в одной
транзакции с записью. Если отправка не удалась или слот пропущен, события остаются в очереди и попадают в
следующее сообщение: релизы не теряются и не дублируются.

**Кто потребляет события `release`.** Если `digest.releases_message: true`, основной дайджест релизы не показывает
и не потребляет, независимо от `digest.insights`: события принадлежат сообщению с релизами. Если
`releases_message: false`, поведение релизов в основном дайджесте не меняется (как сегодня).

**Комбинации флагов** (оба по умолчанию `false`):

| `insights` | `releases_message` | Результат |
|---|---|---|
| false | false | как сегодня, ничего не меняется |
| true | false | новый формат основного дайджеста; релизы в нём остаются как сегодня, в конце секции и в общем лимите (иначе они потерялись бы) |
| false | true | старый формат основного дайджеста, но без релизов; релизы идут отдельным сообщением |
| true | true | целевая конфигурация из макетов |

`repka doctor` предупреждает, если включён только один из флагов (это не ошибка).

**Невыданные пункты (`…and N more`).** Overflow-пункты 🆕/🔎/📈 остаются в очереди, пока не будут показаны.
Чтобы очередь не росла без границы и старые «новинки» не всплывали, вводится `digest.pending_max_age`
(по умолчанию `7d`): пункт старше этого возраста тихо помечается обработанным без показа. Это действует только
при `digest.insights: true`; при `false` поведение прежнее (overflow помечается обработанным сразу).

**Команды.** `repka digest --more` и `repka releases --since 24h` только читают и ничего не помечают
обработанным. `--more` печатает невыданные пункты в очереди (не только последнего отправленного дайджеста), с теми же
отметками. `releases --since` читает таблицу `events` (`kind = release`), независимо от того, отправлено событие
или нет. Builder проверяет, что события не удаляются раньше, чем нужно для окна `--since`; если удаляются, вопрос
хранения решает builder и сообщает владельцу.

**Слот релизов.** `digest.releases_slot` по умолчанию `"09:00"` (локальное время, настраивается). Пропущенный слот
подчиняется тому же `digest.max_lateness`, что и обычные слоты: если он старше, сообщение пропускается, а события
остаются в очереди и уходят в следующий слот (поэтому окно «за сутки» может в такой день включать больше). Это не
потеря: релизы остаются в очереди.

**Решение владельца о YAML.** Вопросы в `domains/*.yaml` остаются; перетриаж 9519 репозиториев при ближайшем
плановом запуске принят и не зависит от флагов. Оценка по результатам (раздел ниже).

## Отклонения реализации от спецификации

- **Ключ записи релизов.** Вместо уникального ключа `(kind, slot, local_date)` ключ остаётся `(slot, local_date)`.
  Запись сообщения с релизами хранит `slot = 'releases:HH:MM'` и `kind = 'releases'` (колонка `digests.kind`,
  миграция 004, по умолчанию `main`); основная запись хранит обычный слот `HH:MM`. Причина: на `digests`
  ссылаются `events` и `digest_items`, пересборка таблицы ради нового ключа не оправдана. Правило префикса:
  `digest/slots.py` `slot_key(kind, slot)`, `recorded_slots(kind=...)` снимает префикс.
- **Пометка pre-release снята.** В payload события `release` (`tag`, `name`, `published_at`, `url`) такого поля нет,
  поэтому в сообщении она не показывается (как и было оговорено для случая «данных нет»).
- **Overflow по типам.** При `insights: true` невыданные пункты `new`/`found`/`release` остаются в очереди (до
  `pending_max_age`, одинаковый срок для `new_repo` и `release`); по-прежнему помечаются обработанными только
  невыданные `stack`. Причина для `release`: строка таблицы флагов «релизы остаются в основном дайджесте», иначе они
  терялись бы ежедневно (релизы идут последними и делят лимит домена с группой new). `repka digest --more` печатает
  очередь (безлимитная сборка, только `new`/`found`/`release`), а не разницу с обычной сборкой. Движущиеся (📈) не
  связаны с событиями, очереди у них нет.
- **Окно релизов.** `repka releases` читает `events.kind = 'release'` по `detected_at`; события не удаляются
  раньше, чем нужно для окна, отдельного решения по хранению не потребовалось.

## Ограничения

- Все глобальные ограничения `CLAUDE.md` проекта: сеть только GitHub и Telegram, секреты только в `.env`,
  `textutil.printable()` для терминала и `textutil.html_escape()` для Telegram (описания репозиториев это
  недоверенный текст), репозитории идентифицируются по числовому id.
- Тесты не ходят в сеть; фикстуры в `tests/fixtures/`, фейки через `pipeline.Boundaries`.
- Один проход не должен падать из-за отсутствия facet-ответов: репозиторий без ответов выводится без отметок.
- Ответы лежат в `verdicts.answers_json`; берётся последний вердикт домена по `decided_at`
  (как делает `_latest_verdicts` в `src/repka/digest/build.py`).
- Лимиты длины Telegram уже обрабатываются разбиением на части (`parts`); новые сообщения должны вписываться в тот же механизм.
- Коммиты только с одобрения владельца (глобальное правило пользователя). Проектное правило, разрешающее агентам
  коммитить и пушить, здесь отдельно не подтверждалось.

## Оценка (по результатам)

После завершения перетриажа посмотреть по каждому facet-вопросу распределение `p`: доля репозиториев с `p >= 0.7`.
Вопрос, у которого почти все «да» или почти все «нет», это шум: заменить или отключить (`enabled: false`).
Ручная выборка: 10 репозиториев с высоким `p` и 10 с низким, сверить с README. Решение о замене слабых вопросов
принимает владелец.

## Оставлено builder'у

- Структура кода, имена ключей и команд (кроме отмеченных как предложение), формат хранения «не показанных»
  пунктов.
- Изменения стека (`stack_changed`) в основном дайджесте: в макете их нет, не обсуждались; по умолчанию оставить
  как сегодня, в конце секции.
- Порядок внутри секции: сохранить текущий (substance, relevance, звёзды для новых; рост за сутки для 📈), если
  не найдётся причины менять.
- Пометка pre-release в релизах: показывать, только если данные есть в payload события `release`; иначе не показывать.
- Один релиз на репозиторий в сутки: показывается самый новый тег.
- Язык подписей и заголовков: английский, как сейчас (моё решение; перевод возможен позже).

## Известные побочные наблюдения (вне объёма)

- Поле `kind` часто ставится как `framework` у MCP-серверов, которые скорее `tool`.
- В случайной выборке принятых репозиториев `mcp` есть те, что по описанию не похожи на MCP
  (gflow, axonasp, vi-sql): возможны ложные срабатывания `relevant`. Требует отдельной проверки.
